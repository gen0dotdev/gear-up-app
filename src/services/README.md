# services/ ชั้น Business Logic

กฎของร้านอยู่ที่นี่: จองได้ไหม ย้ายได้ไหม ปิดงานได้ไหม ช่องเหลือเท่าไร

- **ไม่ import Express** ไม่รู้จัก `req`, `res` หรือ Status Code
  ฟังก์ชันที่นี่จึงเรียกได้จาก Route, จาก Test ตรง ๆ, จาก Script หรือจาก Astro ในคอร์สสุดท้าย
- **รับ `db` เป็นพารามิเตอร์ตัวแรก** ไม่ import ฐานข้อมูลเอง
  ตอนรันจริง `db` คือ Neon ตอน Test คือ PGlite ในหน่วยความจำ โค้ดชุดเดียวกัน
- **ทำไม่ได้ → `throw` `ServiceError`** (`errors.ts`) ที่บอกแค่ชนิด (`not-found`, `conflict`, `invalid`)
  `middleware/error-handler.ts` เป็นคนแปลงเป็น `404` / `409` / `400`
- **ใช้กฎจาก `rules/`** (`baysLeft`, `isPast`, `canChangeStatus`, `canDoService`) ไม่เขียนกฎซ้ำ
  ถ้ากฎเดียวกันอยู่สองที่ วันหนึ่งสองที่จะตอบไม่ตรงกัน
- **ไม่มี Transaction หรือการล็อกในโฟลเดอร์นี้** (ดูหัวข้อถัดไป)

## ทำไม "ไม่เกิน 4 คัน" ไปรับประกันใน `db/`

การนับว่ารอบยังว่างกับการบันทึกต้องเป็นงานเดียวกัน ไม่อย่างนั้นสองคนที่กดจองช่องสุดท้ายพร้อมกันจะเข้าได้ทั้งคู่
แต่ละฐานข้อมูลทำงานเดียวแบบนี้ต่างกัน: Postgres ใช้ Transaction + ล็อกแถวของรอบ (`SELECT ... FOR UPDATE`)
ส่วน D1 ในคอร์ส fullstack-astro ไม่มี Transaction แบบโต้ตอบ จึงใช้คำสั่งเดียว
`INSERT ... SELECT ... WHERE (นับการจองที่ใช้ช่องในรอบ) < 4`

ถ้าโค้ดแบบ Postgres อยู่ในไฟล์ของ services ตรงนี้ การย้ายไป D1 ต้องแก้กฎของร้านด้วย จึงย้ายวิธีไปไว้ใน
`db/queries/booking-writes.ts` (`insertBookingIfRoom`, `moveBookingIfRoom`) ซึ่งตอบผลเป็นค่าธรรมดา
`"ok"`, `"full"`, `"same-car"` (และ `"not-booked"` ตอนย้าย) แล้ว `create-booking.ts` กับ `move-booking.ts`
แปลงผลนั้นเป็น `ServiceError` เอง services ทั้งโฟลเดอร์จึงย้ายไป D1 ได้โดยไม่ต้องแก้ นี่คือประโยชน์ของการแยกชั้น

## ทำไมราคาถูก "ล็อก" ไว้ตอนจอง (`bookings.price`)

ร้านจริงตกลงราคากับลูกค้าตอนรับจอง ถ้าคุณภูมิขึ้นราคาน้ำมันเครื่องจาก 1,200 เป็น 1,300 คืนนี้
ลูกค้าที่จองไว้แล้วต้องจ่าย 1,200 ตามที่เห็นตอนกดจอง ไม่ใช่เจอราคาใหม่ตอนมารับรถ
และยอดขายย้อนหลังต้องไม่เปลี่ยนเองเมื่อแก้ราคา `create-booking.ts` จึงคิดราคาจากตาราง `services`
และขนาดรถ **ครั้งเดียวตอนจอง** แล้วเก็บไว้ในการจอง ย้ายรอบก็ไม่คิดราคาใหม่
การแก้ราคา (`catalog.ts`) มีผลกับการจองใหม่เท่านั้น ร้านค้าออนไลน์ทำแบบเดียวกัน (ราคาในใบสั่งซื้อ ≠ ราคาในหน้าสินค้า)

## เบอร์ของการจอง (`bookings.phone`) ไม่ใช่เบอร์ของเจ้าของรถ

คนที่พารถมาอาจไม่ใช่เจ้าของรถในระบบ (ลูกพารถพ่อมา) "การจองของฉัน" จึงเทียบรหัสจองกับเบอร์ที่กรอกตอนจอง

## ช่างของการจองจากลูกค้า

ลูกค้าไม่เลือกช่าง การจองใหม่จึงยังไม่มีช่าง (`mechanic` เป็น `""`, `mechanicId` เป็น `null`)
คุณขวัญมอบหมายช่างบนกระดานงานด้วย `assignMechanic(db, bookingId, mechanicId)` (`assign-mechanic.ts`):

- ได้เฉพาะการจองที่ยังเป็น `booked` (งานที่ปิดหรือยกเลิกแล้วเป็นประวัติ) → ไม่ใช่ `409`
- ช่างต้องมีอยู่จริง → ไม่มี `404`
- ช่างต้องทำบริการนั้นได้ ตาม `mechanics.services` (ช่างโอมไม่รับน้ำมันเครื่อง) → ไม่ได้ `409`
  กฎนี้อยู่ใน `rules/` (`canDoService`)
- `mechanicId` เป็น `null` = เอาช่างออก

| ไฟล์ | งาน |
| --- | --- |
| `catalog.ts` | รายการบริการ, คุณภูมิแก้ราคาและเวลา (มีผลกับการจองใหม่) |
| `slots.ts` | ช่องว่างและข้อความของแต่ละรอบ |
| `create-booking.ts` | ลูกค้าจอง: เช็กบริการและรอบ ล็อกราคา แล้วให้ `insertBookingIfRoom` บันทึก |
| `guest-booking.ts` | "การจองของฉัน": ดูและยกเลิกด้วยรหัสจอง + เบอร์โทร |
| `board.ts` | กระดานงานของวัน |
| `move-booking.ts` | ย้ายรอบ (กฎเดียวกับการจองใหม่) ผ่าน `moveBookingIfRoom` |
| `change-status.ts` | `booked` → `cancelled` หรือ `done` เท่านั้น |
| `assign-mechanic.ts` | มอบหมายช่าง (หรือเอาออก) ตามบริการที่ช่างทำได้ |
| `mechanics.ts` | รายชื่อช่างและบริการของแต่ละคน |
| `booking-code.ts` | สุ่มรหัสจอง `GU-XXXX` |
| `errors.ts` | `ServiceError` |
